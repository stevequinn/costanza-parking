## Design Specificity Verdict

**Partially grounded.** The data layer is unambiguously Melbourne (APIs at `data.melbourne.vic.gov.au`, timezone logic, search scoped to Melbourne). However, the **visual language is category-interchangeable**. Glass morphism, green/red status colors, bottom sheet pattern, and filter pills would work unchanged for a bike-share app, EV charger map, or any urban utility. There is no Melbourne-specific visual identity—no laneway culture, no PTV palette, no distinctive wayfinding system.

**Deterministic scan**: 1 antipattern detected—Inter font flagged as overused (line 11, `font-family: 'Inter'`). Legitimate finding; Inter is so common it no longer feels distinctive. No false positives.

---

## Overall Impression

A functional, well-engineered parking utility with solid domain logic (Melbourne time handling, restriction parsing, progressive detail reveal) wrapped in a generic, category-interchangeable shell. The single biggest opportunity: **make the loading experience match the quality of the data pipeline.** If 40% of first-time users close the app during the gray "Initializing..." spinner, the entire Web Worker + IndexedDB + caching architecture is irrelevant.

---

## What's Working

1. **Melbourne-aware time logic** (lines 221–265): `isCurrentlyActive()` correctly handles day ranges, time windows, and all-day restrictions. Genuinely useful domain logic, not a template.
2. **Progressive detail reveal**: The "Active Now" vs "Other Times" split (lines 717–750) answers the most urgent question first. Smart IA.
3. **Performance architecture**: Web Worker + IndexedDB caching + `requestIdleCallback` rendering + 1000-marker cap shows real engineering consideration for mobile constraints.

## Priority Issues

### P0 — No Auto-Refresh or Staleness Indicator
**What**: Parking data decays in minutes. The app fetches once and never tells the user how old the data is. The "Updated" timestamp (line 703) shows `lastupdated` which may be stale sensor time, not data fetch time. No auto-refresh, no refresh timer, no "data is X minutes old" warning.

**Why it matters**: A user sees "FREE" on a bay, walks 3 blocks, and finds it occupied. Trust destroyed. The "Reload Sensors" button exists but there's no prompt to use it.

**Fix**: Add a visible staleness indicator (e.g., "Updated 2 min ago" with auto-refresh every 60s). Show a warning badge when data is >5 minutes old. Add pull-to-refresh gesture on the map.

**Suggested command**: `$impeccable harden`

---

### P1 — Bottom Sheet Lacks Swipe Gesture
**What**: Only the handle tap (line 825–831) toggles the sheet. On mobile, users expect to swipe up/down on the sheet itself.

**Why it matters**: Platform convention violation. Users will try to swipe the sheet and nothing happens. For a mobile-first utility, this feels broken.

**Fix**: Add touch event listeners for swipe-to-expand/collapse on the bottom sheet area. Use `touchstart`/`touchmove`/`touchend` with velocity detection for natural feel.

**Suggested command**: `$impeccable animate` or manual implementation

---

### P1 — Search Results Not Keyboard-Navigable
**What**: Lines 897–904 add click handlers but no `keydown`/`arrow`/`enter` support. A user who tabbed into search cannot select a result without a mouse.

**Why it matters**: Accessibility violation. Keyboard-only users (and screen reader users) cannot use the primary search function.

**Fix**: Add `role="listbox"` to results container, `role="option"` to each result, arrow key navigation, Enter to select, Escape to close.

**Suggested command**: `$impeccable adapt`

---

### P2 — "Near" Stat Card Creates False Context
**What**: When no location is set, it shows "0" with no explanation (line 167–169). When location is set, it silently changes meaning.

**Why it matters**: Confuses users. "Near" is context-dependent but presented as a global metric alongside Total/Free/Taken.

**Fix**: Hide the "Near" card until geolocation is active. Or replace with a always-relevant metric (e.g., "Visible" count of bays on screen).

**Suggested command**: `$impeccable distill`

---

### P2 — Error States Are Ephemeral
**What**: Worker errors (line 536) and geolocation denial (line 852) display as status text that gets overwritten by the next status update. No persistent error state, no retry mechanism.

**Why it matters**: Users see an error flash and then it's gone. They have no idea what went wrong or how to fix it.

**Fix**: Persist error states in a dedicated error banner with retry action. Don't overwrite errors with status updates.

**Suggested command**: `$impeccable harden`

## Persona Red Flags

### Jordan (First-Timer / Stressed Driver)
- Opens app → gray spinner with "Initializing..." → no ETA → abandons
- Taps map randomly → nothing happens at low zoom → thinks app is broken
- Finds "Free" badge → wants to navigate there → no "Open in Maps" action
- **Critical**: No onboarding, no first-use hint, no indication the map is tappable

### Casey (Mobile / Commuter)
- One-handed use → search input is small (`py-3`), keyboard covers bottom sheet
- Taps "Reload Sensors" while walking → no confirmation → accidentally triggers slow re-fetch
- Filters to "Free" → taps dot → hits Back → filter active but scroll position lost
- **Critical**: No haptic feedback on bay selection, pulse animation too subtle

### Riley (Stress Tester)
- Searches "123 Smith St" → 6 Nominatim results → all full addresses → must tap each to find right one
- Poor connectivity → worker fails silently → error overwritten by "Updated" timestamp → user thinks data is fresh
- **Critical**: Race condition between `scheduleRender` and rapid map panning

## Questions to Consider

1. **Is a map the right primary interface?** Most stressed drivers want "nearest free spot to where I'm going" — a list sorted by distance from a typed address might be faster than interpreting a dot map.

2. **Why no "Navigate here" CTA?** The app answers "where can I park?" but drops the user at "okay, now what?" — an intent gap between discovery and action.

3. **Should the app show restriction confidence?** Sensor data says "not present" but the sign says "2P 8am–6pm" — which does the user trust? The current disclaimer is buried and passive.

4. **Is 600m the right nearby radius?** In Melbourne's CBD, 600m could be 8 blocks. In Fitzroy, it's 2 blocks. Should this adapt to density or zoom level?

5. **What's the cost of the current loading experience?** If 40% of first-time users close the app during "Initializing...", the entire data pipeline is irrelevant.
